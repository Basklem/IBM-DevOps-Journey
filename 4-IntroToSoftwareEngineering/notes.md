# Introduction to Software Engineering — Notes

## Key Takeaways
- **Software engineering** = applying scientific/engineering principles to systematically gather requirements and design, build, and test software; it's broader in scope than **software development**, which focuses on implementing specific functionality.
- The mid-1960s–mid-1980s **software crisis** (over budget, late, buggy, unscalable code) is what pushed the industry from ad hoc coding toward a real engineering discipline — including the rise of **CASE** tools.
- Titles (engineer/developer/programmer) are used inconsistently across companies and countries — in some places "engineer" is a formally regulated title (ethics codes, licensing); in the US it's mostly informal. The common thread: engineering implies the *full lifecycle* (design → build → maintain → evolve) and system-level thinking, not just writing code.
- The **SDLC** (Software Development Life Cycle) is the standard framework for building high-quality software predictably — six phases (**planning, design, development, testing, deployment, maintenance**), each discrete with its own deliverables. Originally linear (**Waterfall**), now commonly run iteratively.
- Planning produces the **SRS** (Software Requirements Specification); design produces a **design document**; both are key gate deliverables before coding starts.
- Testing splits into three types (**functional, non-functional, regression**) across four levels (**unit → integration → system → acceptance/UAT**); releases then progress through **alpha → beta → GA** audiences.
- **Requirement gathering** is a 6-step process: identify stakeholders → set goals & objectives → elicit → document → confirm → prioritize. It can produce up to three documents: **SRS** (most common), **URS** (user stories), and **SysRS** (whole-system requirements, broader than SRS).
- Requirements split into four categories: **functional, external/UI, system features, non-functional**.
- Three common development methodologies: **Waterfall** and the **V-shape model** are both sequential (upfront planning, hard to change once underway); **Agile** is iterative (short sprints, changing requirements handled easily, but harder to budget/scope upfront). Agile is the most widely used today.
- Software **version numbers** track release/update history — often 2–4 dot-separated number sets; **semantic versioning** = major.minor.patch.build. Check version numbers first when troubleshooting compatibility issues.
- Documentation splits into **product** (what the software does — requirements, design, technical, QA, user docs) vs. **process** (how to do a task, often detailed further in an **SOP**). Keep it updated during maintenance.
- Common project roles: **project manager/Scrum master, stakeholder, architect, UX designer, developer, tester/QA, SRE/Ops, product manager/owner, technical writer** — names vary by org/methodology, and in practice these roles work best tightly collaborating rather than handing work off in sequence.
- A website/cloud app request-response flow: browser → server → **HTML** (structure) + **CSS** (style) + **JavaScript** (interactivity), mixing **static** and **dynamic** content. Dev work splits into **front-end** (client-side, HTML/CSS/JS + frameworks like Angular/React/Vue), **back-end** (server-side logic, auth, databases, APIs/routes/endpoints, e.g. Node.js/Express or Python/Django/Flask), and **full-stack** (both) — the two sides must collaborate closely since each depends on the other's contract.
- Good **teamwork** (trust, clear goals/roles, playing to strengths, solid communication) drives better code quality, fewer bugs, shared knowledge, and reduced stress; Agile orgs often call a small cross-functional team a **squad**.
- **Pair programming** (driver/navigator, ping-pong/TDD, or strong-style for mentoring) trades short-term speed for fewer bugs, faster onboarding, and shared knowledge — but needs real scheduled time and works best when neither partner dominates.
- A dev's core toolkit: **version control** (Git/GitHub — track changes, branch, merge), **libraries** (reusable code you call, e.g. jQuery), and **frameworks** (a scaffold that calls your code and dictates architecture, e.g. Angular/Vue/Django — choose early, since frameworks are hard to swap in mid-project).
- **CI/CD** automates integration and delivery; **build tools** turn source into binaries and manage dependencies; **packages** bundle an app for distribution via a **package manager** (npm, pip, Maven, Homebrew, etc.).
- A **software stack** is a layered set of technologies (front-end + back-end) that work together to run an app — common named stacks include **LAMP**, **MEAN**, **MERN**, **MEVN**, Python/Django, Ruby on Rails, and ASP.NET. All-JavaScript stacks (MEAN/MERN/MEVN) trade relational-DB power for single-language simplicity; LAMP trades flexibility for maturity and relational data support.
- In practice, **Git/GitHub is nearly universal**, VS Code + linters/formatters (ESLint, Prettier) are a common baseline setup, and **React**, **Angular**, **Node.js/Express**, and **jQuery** dominate practitioner mentions — often paired with clean, modern (ES6) JavaScript practices.
- Programming languages split into **interpreted/scripting** (translated to machine code at runtime by an interpreter — JavaScript, Python, Lua; used for lighter, cross-platform scripts) vs. **compiled** (translated ahead of time into one executable — C/C++/C#, Java; used for larger, more complex programs like operating systems).
- A second axis: **high-level languages** (English-like, faster to write/debug — query languages like SQL, structured languages like PASCAL, OOP languages like Python) vs. **low-level languages** (**assembly** — symbols mapped closely to machine code, CPU-specific (ARM/MIPS/x86), translated by an **assembler** with a 1:1 statement-to-machine-instruction ratio).
- **Query languages** (SQL most common) request or manipulate database data via **select** (retrieve) vs. **action** (create/insert/update) statements — covering **CRUD**; **SQL** databases are relational with fixed schemas, **NoSQL** databases are non-relational with dynamic schemas for unstructured data.
- Planning code before writing it improves quality and maintainability, via **flowcharts** (pictorial, good for smaller problems and early-stage communication) or **pseudocode** (language-agnostic logic description, better for larger projects, beginners, and cross-team review).
- **Branching** (if / if-else / switch / GoTo) picks *what* code path runs based on Boolean conditions; **looping** (while / for / do-while) picks *how many times* a block repeats until a condition is met.
- Core programming building blocks: **identifiers** (**constants** = fixed values, **variables** = changeable values), **containers** (**arrays** = fixed-size/same-type/sequential, **vectors** = dynamically resizable arrays), **functions** (reusable, single-purpose code — built-in/library or custom), and **objects** (OOP's data+behavior bundles — properties/fields plus methods — vs. procedural code, which keeps functions and data separate).
- **Software architecture** = the system's blueprint/organization — the earliest, costliest-to-change design decisions, addressing non-functional needs (performance, scalability, security, etc.) and driving tech-stack and production-environment choices; documented via the **SDD**, **architectural diagrams**, and **UML diagrams**.
- **Structured design** breaks a system into cohesive, loosely-coupled **modules**; **UML** (structural + behavioral diagrams, programming-language-agnostic) is the standard way to visualize a system's structure and behavior before coding, easing planning, onboarding, and code navigation later.
- **OOAD** designs systems around interacting **objects** built from **classes** (blueprints, instantiated into objects with actual property values); a **class diagram** shows classes, their attributes, and **inheritance** relationships between parent classes and subclasses.
- Apps are built from layered building blocks: **objects → components → services** — a **component** is reusable/independent/encapsulated, a **service** is a component with one always-running instance shared by many clients, and **SOA** wires loosely-coupled services together over a network into **distributed systems** (fault-tolerant, concurrent, scalable, appearing as one coherent system to end-users).
- Five core **architectural patterns**: **2-tier/client-server**, **3-tier/n-tier** (presentation → application → data), **peer-to-peer** (every node is both client and server), **event-driven** (producer → event router → consumer), and **microservices** (independent services + API gateway + orchestration) — combinable, though not every pairing works (e.g., P2P can't also be 2-tier).
- Apps move through **pre-production environments** (development → QA/testing → staging) before **production** (the full stack, sized for real load plus non-functional requirements); deployed **on-premises** or to the **cloud** (public, private, or hybrid).
- A production deployment's infrastructure typically layers **firewall → load balancer → web servers → app servers/proxy servers → database server(s)**, each with a distinct job (security, traffic distribution, content delivery, business logic, request routing, data storage).
- **Software engineers** split into **back-end/system developers** (build the underlying systems/networks) and **front-end/application developers** (client-facing UI); day-to-day work spans designing, coding, testing, optimizing, maintaining, and documenting software (plus deployment for DevOps roles) — responsibility scope widens from a narrow slice of code (junior) to whole solution areas including planning/design (senior).
- Engineers need both **hard skills** (technical, learned, certifiable — languages, version control, cloud, testing/debugging, CI/CD, agile, DB architecture) and **soft skills** (teamwork, communication, time management, problem-solving, adaptability, openness to feedback) — every real role blends both.
- Practitioner career advice: build real projects (not just study), pick a business domain you actually care about, treat the job hunt as its own parallel-track skill rather than something to start after "finishing" learning, and stay skeptical of buzzword-driven hype; for women in the field specifically, it's fair to vet a team's diversity commitments up front, insist on being compensated/titled for the work you actually do, and leave environments that aren't genuinely supportive.
- Software engineering demand is broad and durable (nearly every industry needs software, plus IoT growth) — strong US job growth (~22%, 2020–2030), a degree isn't strictly required anymore, and salaries run well above the national average, with employment options ranging from full-time to contracting, freelancing, and open-source volunteering.
- A typical career runs **junior → engineer → senior**, then splits **technical** (staff engineer → principal engineer/architect) vs. **managerial** (technical lead → engineering manager → director → CTO) — though the underlying skills transfer well into adjacent roles (sales/support, data, QA), and real-world entry paths into the field are often non-linear and don't require a CS degree.
- "Software engineer" is an umbrella term covering distinct specialized titles — **front-end, back-end, full-stack, DevOps, QA, integration, security, mobile, games** — each with its own focus and skill set.
- The **IEEE-CS/ACM Software Engineering Code of Ethics** defines eight principles (**public, client/employer, product, judgment, management, profession, colleagues, self**) meant to guide — not replace — an engineer's own professional judgment.

### Module 1: The Software Development Lifecycle

#### Section 1: Overview of Software Engineering

**What is Software Engineering?**
- **Software engineering**: the application of scientific principles to design and create software — a systematic approach to gathering/analyzing business requirements, then designing, building, and testing software to meet them.
- History: computing began in the late 1950s with software engineering as an undefined discipline; it became a formal field in the 1960s as methods shifted from ad hoc programming toward standardized practices.
- The **software crisis** (mid-1960s–mid-1980s): rising demand for complex software outpaced immature development processes — projects ran over budget and behind schedule, produced unmanageable/buggy code, and often didn't scale from small systems to large ones. (Some of this still happens today, just far less often.)
- The fix was treating software development as a real engineering discipline, plus the mid-1980s rise of **CASE** (Computer-Aided Software Engineering) tools, spanning six categories: business analysis/modeling, development tools (e.g., debuggers), verification & validation, configuration management, metrics/measurement, and project management.
- **Software engineer vs. software developer**: often used interchangeably, but engineers typically have broader knowledge, take a systematic/big-picture approach, and build entire systems on larger-scale projects; developers tend to work more creatively on specific functionality within a system.
- SE responsibilities: designing, building, and maintaining software systems; writing and testing code; consulting with stakeholders (clients, vendors, security specialists, other team members).
- Modern development is typically guided by the **SDLC**, covered next.

**Insider's Viewpoint: What is Software Engineering?**
- *(Practitioner opinions, not a formal definition — useful for context on how the term is actually used in industry.)*
- Software engineering spans many specializations: front end, back end, security, mobile, test, full stack, DevOps, cloud, data, ML.
- Common theme across the practitioners: it's the *full lifecycle* — design/architecture, implementation, and ongoing maintenance/evolution — not just writing code; several described it as a creative, end-to-end process starting well before code is written and continuing after deployment.
- Consensus on engineer vs. developer: "engineer" implies a longer time horizon and broader responsibility (system design, architecture, data flow), while "developer" is more narrowly scoped to building features/apps from an assigned task.
- Title usage varies a lot by company and country — in the US, "engineer/developer/programmer" are often interchangeable and inconsistently gatekept; in Canada, "engineer" is a regulated title requiring specific ethics training, similar to civil/mechanical engineering.

**Introduction to the SDLC**
- **SDLC (Software Development Life Cycle)**: a systematic process for developing high-quality software within a predictable timeframe/budget, aimed at meeting the client's business requirements.
- Defines discrete phases (each with its own process and deliverables) in a planning → design → development cycle that can be run iteratively.
- History: took shape in the mid-1960s as growing software complexity demanded a more deliberate approach; originally used the linear **Waterfall method**, later adapted toward iterative approaches to handle shifting requirements.
- **Key advantages**: replaces ad hoc development with a repeatable process (lower risk, higher efficiency); discrete, well-defined phases so teams know what to work on and when; better communication between customers, stakeholders, and the dev team; supports iteration to incorporate new requirements; catches problems early (in design, not mid-coding); clearly defined roles reduce conflict and overlap.

**Phases of the SDLC**
- Six phases: **Planning → Design → Development → Testing → Deployment → Maintenance**. Each is discrete (no task overlap between phases); names/count can vary by organization.
- **Planning**: requirements are gathered, analyzed, documented, and prioritized. Considerations: users, purpose, data in/out, legal/regulatory compliance, risk, QA needs, resource allocation, scheduling. Costs are estimated against time constraints; teams and roles are proposed. **Prototypes** (small-scale replicas used to gather feedback and test basic design ideas) may be built here — though they can occur at any phase whenever requirements need clarifying. Output: the **SRS** (Software Requirements Specification), which must be understood and approved by all stakeholders.
- **Design**: SRS requirements are turned into software architecture by the team, reviewed by stakeholders. Prototypes here are more like preliminary mock-ups for demonstration. Output: the **design document**, used to drive development.
- **Development** (aka building/implementation): coding starts once the design document is done; project planners assign coding tasks from it. Involves specific tools, languages, stacks, and org coding standards.
- **Testing**: code is tested (manually, automated, or hybrid) for stability, security, and conformance to the SRS; bugs are reported, tracked, fixed, and retested across the testing levels detailed in Section 2 of this module.
- **Deployment**: the application is released to production. Often staged — first to a **UAT** (User Acceptance Testing) environment, then to production after customer sign-off. Applies to websites, app stores, or internal distribution servers.
- **Maintenance**: post-deployment — surfaces missed bugs, UI issues, and requirements gaps; identifies enhancements. High-priority bugs get fixed immediately; others feed into a future release, restarting the cycle.

**Building Quality Software**
- Six common SE processes: **requirements gathering, design, coding for quality, testing, releases, documenting.**
- **Requirements gathering** → the **SRS**, which may include use cases describing business needs/user flows. Requirements fall into four categories, detailed in the Requirements section below.
- **Design**: translates requirements into an implementable structure. The technical lead breaks requirements into components (behaviors, boundaries, interactions) that define the system architecture — covering system functions, performance, security, platform characteristics, business rules, application logic, API design, UI, and database design.
- **Coding for quality**: quality code is maintainable, readable, testable, secure, defect-free, clean, consistent, documented, and efficient. Practices: follow coding standards/conventions/patterns, use **linters** to catch programmatic/stylistic errors, and comment code for others.
- **Testing**: verifies the software matches requirements and is bug-free, ensuring reliability, security, performance, and efficiency — across the same testing types and levels detailed in the Software Testing section below (Section 2 of this module).
- **Releases** progress through three audiences: **alpha** (first working version, select stakeholders, likely buggy/incomplete, design may still change) → **beta**/limited release (external stakeholders, real-world testing, should meet all functional requirements) → **GA** (general availability, stable version, all users).
- **Documentation**: spans technical audiences (READMEs, inline comments, architecture/design docs) and non-technical end-users (guides, tutorials, help content) — the fuller product-vs-process framework is covered in the Software Documentation section below.

**Requirements**
- **Requirement gathering** = a six-step process: identify stakeholders → establish goals & objectives → elicit requirements → document → analyze/confirm → prioritize.
- **Stakeholders** typically come from the requesting organization — decision-makers, end-users, sysadmins, engineering, marketing, sales, customer support. Aim for a representative from every affected group.
- **Goals** = broad, long-term, achievable outcomes (customer + business goals). **Objectives** = specific, actionable, measurable steps that achieve those goals.
- Eliciting (via surveys, questionnaires, interviews), documenting, and confirming are usually done iteratively together. Confirmed requirements must be analyzed for consistency/clarity/completeness, then approved by stakeholders.
- **Prioritization** uses labels like "must-have," "highly desired," "nice to have," ideally ordered within each category.
- Requirement gathering can produce up to three documents:
  - **SRS (Software Requirements Specification)** — the most common. Captures the functionalities the software should perform plus performance benchmarks/service levels. Contains: a purpose statement (intended use, audience, scope), constraints/assumptions/dependencies, and requirements sorted into four categories — **functional** (what the software does), **external/UI** (behavior toward users, other hardware/software), **system features** (a required subset of functional requirements), and **non-functional** (performance, safety, security, quality standards).
  - **URS (User Requirements Specification)** — business need and end-user expectations, written as user stories/use cases answering *who*, *what function*, and *why*. UAT determines if these are met. Often folded directly into the SRS rather than kept separate.
  - **SysRS (System Requirements Specification)** — broader than the SRS; covers the entire system, not just the software. Includes system capabilities, interfaces, user characteristics, policy/regulation/personnel/performance/security requirements, system acceptance criteria, and hardware expectations. Most software projects only produce an SRS, not a full SysRS.

#### Section 2: The Software Building Process and Associated Roles

**Software Development Methodologies**
- Three common approaches: **Waterfall**, **V-shape model**, **Agile**.
- **Waterfall**: sequential — each phase's output feeds the next, all planning done upfront, customer doesn't see the product until testing. Major releases repeat this whole cycle, so releases are years apart.
- **V-shape model**: also sequential, shaped like a V. Descending the left side (**verification**): planning → system design → architecture design → module design, bottoming out at coding. Ascending the right side (**validation**): unit → integration → system → acceptance testing — each validation phase corresponds to a verification phase, with tests written on the left and executed on the right.
- **Agile**: iterative — short sprints (1–4 weeks) instead of one long linear pass; unit testing happens every sprint; ends in a **sprint demo**/feedback stage instead of a maintenance phase, then repeats. After several sprints, an **MVP** is built to validate assumptions with stakeholders. Grounded in the same four Agile Manifesto values covered in the Agile/Scrum course.
- **Pros/cons**: Waterfall and V-shape are both easy to understand and make budgeting/resourcing easier (planned upfront), but both are rigid — hard to accommodate changed or overlooked requirements once underway (V-shape is even more rigid than Waterfall, though its early test-planning saves time later). Agile handles changing requirements well since planning resets every sprint, but upfront budgeting/scheduling is harder since full scope isn't defined upfront. Agile is the most widely used approach today.

**Software Versions**
- Version numbers track a program's release/update/patch history — useful for both users and developers, and the first thing to check when troubleshooting compatibility issues.
- Typically 2–4 dot-separated number sets. First release is often **1.0**; a beta/testing build can be below 1 (e.g., 0.9). Some projects version by date instead (e.g., Ubuntu 18.04.2 = April 2018, with the third number marking an incremental update).
- **Semantic versioning** (not universal, but common): **major.minor.patch.build** — major = new release/big changes, minor = smaller changes, patch = bug fixes, build = build number/date/minor tweaks.
- Version info is usually in a program's About/Help menu.
- Compatibility between old and new versions is a common problem; some software is **backwards compatible** (older files/programs still work on newer versions).

**Software Testing**
- **Software testing**: integrating quality checks throughout the SDLC to confirm the software meets requirements and is error-free. Built around **test cases** (steps, inputs, data, expected outputs), always written after requirements are finalized.
- Three testing **types**:
  - **Functional**: black-box (no view of source/internals); tests inputs/outputs of the system under test (SUT) against functional requirements; confirms usability, accessibility, and graceful handling of user errors/edge cases.
  - **Non-functional**: tests performance, security, scalability, availability — behavior under stress/concurrent load, cross-OS consistency, disaster recovery, and whether docs match actual behavior.
  - **Regression** (aka maintenance testing): confirms a recent change (e.g., a bug fix) didn't break existing functionality; run after requirement changes or defect fixes. Test-case selection favors areas with frequent defects, heavily used functionality, recent changes, complexity, or flaky (inconsistently passing) history.
- Four testing **levels** (each at a different SDLC stage, to avoid overlap): **unit** (dev-run, function-level, catches construction errors before integration) → **integration** (black-box; tests already-unit-tested modules once combined, catching interaction/communication bugs, logic mismatches, poor exception handling) → **system** (full integrated product, both functional and non-functional, run in a staging environment resembling production) → **acceptance** (formal sign-off against user needs/business processes, usually run by the customer/stakeholders during maintenance).

**Software Documentation**
- **Documentation**: written, video, or graphical material describing what the software is and how to use it — spans the entire SDLC and targets varied audiences (end users, devs, QA, sysadmins, other stakeholders).
- Two categories: **product documentation** (what the product does) vs. **process documentation** (how to complete a task; should define the quality requirements for doing that task right).
- Five types of product documentation: **requirements** (written during planning, for the dev team — includes the SRS/SysRS/user acceptance specs), **design** (written by architects/dev team — conceptual + technical design docs), **technical** (code comments, working papers, engineers' implementation notes), **QA** (test plans, test data, scenarios, cases, strategies, and traceability matrices mapping test cases to requirements), and **user** (FAQs, install/help guides, tutorials, manuals).
- **SOPs** (Standard Operating Procedures) go with process documentation but in much greater, org-specific detail (e.g., a company's exact steps for merging code, beyond generic dev knowledge) — as a flowchart, hierarchical outline, or step-by-step list.
- Documentation must be kept current (e.g., updating docs when a UI changes) — this happens during the maintenance phase and should be reviewed periodically for accuracy.

**Roles in Software Engineering Projects / Insiders' Viewpoint**
- Common roles (names vary by methodology/company; not every project has every one):
  - **Project manager** (Waterfall) / **Scrum master** (Agile): the PM owns planning, scheduling, budgeting, resourcing, execution, and communication; the Scrum master instead focuses on team/individual success and facilitating communication, per Agile's people-over-process value — not on upfront planning.
  - **Stakeholder**: who the product is built for (customer, end-users, decision-makers, sysadmins, other key personnel) — defines requirements, gives clarifying feedback, sometimes joins beta/acceptance testing.
  - **System/software/solution architect**: designs and communicates the architecture — the software's internal structure and technical characteristics — providing technical support across the SDLC.
  - **UX designer**: balances intuitive design with meeting requirements; defines how the software behaves and communicates from the user's perspective.
  - **Developer**: writes the code, implementing the architecture (design doc), requirements (SRS), and UX specs together.
  - **Tester/QA engineer**: writes and runs test cases to find bugs/deficiencies and feeds them back to developers.
  - **Site reliability engineer (SRE)/Ops engineer**: bridges dev and ops — tracks and runs incident meetings, automates systems/processes, troubleshoots, and owns reliability.
  - **Product manager/owner**: holds the product vision, understands client/end-user needs deeply, and leads development toward the value stakeholders want.
  - **Technical writer/information developer**: translates technical material into end-user-facing docs (manuals, reports, white papers, press releases) — helping both end-users and the customer's ability to give useful feedback.
- What practitioners added beyond the formal role list (**Insiders' Viewpoint**):
  - In practice, the product manager often *also* runs Scrum-master-style duties — daily stand-ups, ticket tracking (e.g., JIRA), unblocking engineers, stakeholder updates — even without a formally separate Scrum master title. Project/program managers were highlighted as increasingly important as systems grow larger and more complex.
  - Engineers commonly split informally (or formally, depending on the company) into architecture/big-picture-focused vs. hands-on coding-focused, and further into specialized tracks like DevOps/infrastructure vs. QA/CI-CD automation.
  - Multiple practitioners emphasized that **close, embedded collaboration beats hand-offs** — regular check-ins, shared brainstorming, and cross-role group chats work better than a waterfall-style relay between roles.
  - Typical UX workflow: UX designers hand off specs (e.g., via Figma) that engineers implement, spanning from early sketches through mockups and iteration; separate **UX researchers** are brought in to interview real users/customers for direct feedback.
  - Typical review loop: code goes to a tech lead/senior engineer for review, then to QA for testing; if QA finds something broken, they write up a test plan or detailed bug report so the developer knows exactly what to fix, and the cycle repeats until QA confirms it's resolved.
  - Engineers said they interact most with product managers/owners (sometimes literally an internal customer) for direction and trade-off discussions, and regularly with SREs/sysadmins (deployment/running the software) and dedicated test engineers (end-to-end, automated, integration testing).
  - Overall theme: as systems get more complex, an engineer is never working in isolation — success depends as much on communicating directly with the team as on writing code.

### Module 2: Introduction to Software Development

#### Section 1: Introduction to Development

**Overview of Web and Cloud Development**
- Basic client-server flow: browser sends a URL request to a server; the server responds with **HTML** (structure — functional but plain), **CSS** (style/flair), and **JavaScript** (interactivity/dynamic content).
- Content is **static** (pre-stored, served as-is) or **dynamic** (generated per request, often pulling from databases/other systems) — most sites blend both for the best experience.
- **Cloud applications** work like websites but are built around cloud back-end infrastructure, storage, processing, and other cloud services — making them scalable and resilient.
- Development splits into **front-end** (client-side — what the user sees/interacts with: HTML/CSS/JS + frameworks/libraries/tools) and **back-end** (server-side — logic, functionality, authentication, database work, sometimes alongside DBAs). **Full-stack** developers work both sides.
- Tooling: a code editor is the first must-have tool; **IDEs** add build/compile/debug/integration capabilities, multi-language support, Git/GitHub integration, and custom extensions/themes (e.g., Sublime Text, Atom, Vim, VS Code, Visual Studio, Eclipse, NetBeans).

**Learning Front-End Development**
- Core trio: **HTML** builds the page's physical structure (text, links, images, videos, dividers, buttons) and ensures consistent cross-browser display; **CSS** styles it (fonts, colors, layout, uniformity) and enables cross-browser/cross-device compatibility; **JavaScript** adds interactivity/functionality on top (e.g., making a styled button actually do something).
- CSS extensions: **SASS** (variables, nested rules, inline imports — faster/more organized stylesheets, backward-compatible with CSS) and **LESS** (adds more styles/functions, backward-compatible with CSS; compiled to CSS via LESS.js).
- **Adaptive** design serves a specific pre-built version of a page based on screen size; **responsive** design automatically resizes/adapts the same page to whatever device it's viewed on.
- JavaScript frameworks/libraries: **Angular** (Google, open-source, fast HTML rendering, built-in routing & form validation), **React.js** (Facebook, a UI-component library rather than a full framework — needs third-party tools like routing added separately), **Vue.js** (community-maintained, focused on the view/UI layer, flexible enough to act as either a library or a full framework).
- Front-end work is continuously evolving — sites need to keep working across shifting browsers, OSes, and devices.

**The Importance of Back-End Development**
- Back-end developers build and manage the server infrastructure that processes requests, supplies data, and delivers services securely — everything happening before data/code reaches the client.
- Front-end and back-end devs must collaborate closely, understanding each other's requirements and how their parts interact before and throughout development.
- Real-world example (online shopping): a product search hits a web app that queries a separate database and returns results; restricted areas require account management, authentication, and authorization; checkout requires securely handling sensitive data (address, payment info) — all commonly back-end responsibilities.
- Back-end devs process incoming requests via **APIs** (code that works with data, usually JSON/XML, under set rules/structure), **routes** (the path to a resource, generally taking input and returning results), and **endpoints** (where a request is actually handled — a missing endpoint returns a 404).
- Common back-end languages/frameworks: **JavaScript** (via **Node.js**/**Express**, now used server-side too) and **Python** (flexible, easy to learn, wide use — via **Django**/**Flask**).
- Back-end devs also work heavily with databases — SQL knowledge helps, and **ORM** (Object Relational Mapping) tools simplify querying, though understanding database fundamentals still matters for troubleshooting.
- Overall scope: account management, auth, secure data handling/storage/transfer, and database work — described as challenging and constantly evolving.

**Teamwork and Squads / Insiders' Viewpoint: Teamwork in Software Engineering**
- A **team** = people with varied skills working toward a common goal; teamwork drives creativity (discussing/challenging ideas) and is empowering when attitudes are positive.
- What makes teams work: trust/respect (built over time via equitable contribution), clear and agreed-upon goals, clearly defined roles (avoiding duplicated effort or missed tasks), playing to individual strengths, celebrating wins/analyzing problems, and a communication method that works for everyone.
- What this looks like in practice: kickoff meetings (plan, assign tasks, agree on goals), team/sub-team progress meetings, design/code reviews done by whoever's available, walkthroughs (to the team and to stakeholders), end-of-project retrospectives, mentoring (formal or team-wide), and sometimes dedicated internal-project teams (coding standards, legacy code, evaluating new tools).
- Benefits: more creativity and knowledge-sharing, better adherence to coding standards and documentation (accountability), higher-quality/fewer-bug/more-maintainable code, reduced stress (someone to turn to), and a stronger grasp of the big picture leading to more coherent solutions.
- **Squads**: what Agile orgs often call a team — small (up to 10 devs), typically a squad leader (anchor developer/coach) plus engineers building features/tests, sometimes 1–2 UX designers, and often internal pair programming.
- What practitioners added beyond the lesson: engineering is rarely solo — communication (including negotiating spec changes with a UX designer) is core to the job. Multiple engineers said team-built software is more impactful, more fulfilling, and easier to sustain/maintain long-term than solo work, since a team provides a support structure, diverse perspectives, more checks/balances against mistakes, and the confidence to take bigger risks together. In practice, engineers are in constant contact not just with tech leads but with product managers, UX designers, and business/data analysts — shipping a real product takes many people, and staying in an isolated silo isn't sustainable.

**Pair Programming / Insiders' Viewpoint: Pair Programming**
- **Pair programming**: an extension of teamwork where two developers work side-by-side at one computer (in person preferred, but virtual via video/screen-share also works) — an Agile technique where continual planning/discussion generally produces a better end product.
- Three styles:
  - **Driver/navigator** (most common): the driver types, the navigator reviews in real time and watches the bigger picture; swap roles regularly to keep both engaged.
  - **Ping-pong**: incorporates TDD — one dev writes a failing test, the other writes the code to pass it, then they swap for the next task; both refactor together once a task passes.
  - **Strong-style**: good for mentoring juniors — any idea must pass through someone else's hands to reach the computer, so the more experienced person navigates while the junior drives/learns by doing; the driver shouldn't challenge ideas mid-implementation, to avoid breaking the navigator's flow.
- Benefits: shares knowledge/skills (great for onboarding), builds technical *and* soft skills (communication, problem-solving), fewer typos/logic errors/bugs (two sets of eyes), enables on-the-fly code review (an extra layer, not a replacement for formal review), surfaces multiple initial ideas and tends to converge on the optimal approach earlier, and — despite taking longer upfront — usually nets out to better code with less time spent on review/testing/bug-fixing later.
- Challenges: requires sustained focus (exhausting over long periods), scheduling/availability conflicts, risk of one person dominating (turning it into a "typist/programmer" dynamic instead of true collaboration), personality mismatches, and noise when multiple pairs share a workspace.
- What practitioners added beyond the lesson: pairing with a senior engineer was repeatedly cited as valuable for ramping up quickly on a new team, language, or toolset, for getting real-time feedback instead of waiting on a formal review, and for surfacing each person's individual "blind spots" (everyone has different ones, so pairing catches more than either person would alone) — but it only works well if the senior partner guides without fully taking over. Real frustrations mentioned: differing individual problem-solving styles/workflows can be genuinely annoying to watch, and pairing requires real, dedicated, aligned calendar time — a hard ask under tight deadlines, though it pays off long-term (more people who understand the code, easier future support).

#### Section 2: Tools in Software Development

**Introducing Application Development Tools**
- A developer's "workbench" starts with **version control**, **libraries**, and **frameworks**.
- **Version control**: tracks who changed what and when, and resolves conflicts between changes — worth using even as a solo developer (lets you revert to older versions and see how the code evolved). Since version control is tied to your storage system, a code repository is recommended from day one. **Git/GitHub**: track changes in repositories, branch off for focused work, then merge back into the main codebase.
- **Libraries**: reusable code (standard programs/subroutines) you can drop into your project — e.g., a carousel UI widget — instead of building it yourself. Multiple libraries can be combined as needed; *you* call the library's functions, and control returns to your code afterward — you stay in the driver's seat. Examples: jQuery (DOM manipulation), EmailValidator (validates email format), Apache Commons Proper (reusable Java components).
- **Frameworks**: a standard scaffold you build your app on top of — the reverse relationship from libraries, since the framework calls *your* code and dictates the architecture/program flow. The lesson stresses picking a framework early, since swapping one into an existing project is a heavy lift, not a simple drop-in. Frameworks are less flexible than libraries but give strong standardization. Examples: Angular (JS, dynamic web apps), Vue.js (JS, UI-focused), Django (Python).
- **Inversion of control**: the framework's predefined workflow drives development rather than you driving it directly. "Opinionated" frameworks make more decisions for you (file structure, naming, etc.) — less freedom, but less tedious configuration. Frameworks often bundle their own libraries internally.

**More Application Development Tools**
- **CI/CD**: a DevOps best practice for shipping frequent, reliable changes. **CI (Continuous Integration)** uses a build-automation server to make sure all code components work together, integrating new code frequently (daily or even hourly). **CD (Continuous Delivery/Deployment)** picks up where CI ends — auto-deploying built/tested changes to a staging or production environment.
- **Build tools**: turn source code into installable binaries — organizing code, setting compile flags, and managing dependencies. Most critical in multi-developer, multi-project environments where tracking changes/dependencies/build order by hand gets unmanageable. Automates dependency downloads, compiling, packaging, testing, and deployment; can be triggered from the command line or an IDE.
  - Two categories: **build-automation utilities** (compile/link source into build artifacts) vs. **build-automation servers** (run those utilities on a schedule or trigger).
  - Examples: Webpack (JS module bundler), Babel (JS compiler), WebAssembly (binary format that runs in-browser).
- **Packages**: archive files bundling an app's files, install instructions, and metadata (description, version, dependencies) for easy distribution.
- **Package managers**: find, install, maintain, and uninstall packages on request — coordinating with archivers to extract files, verifying checksums/certificates for integrity, and resolving dependencies from a repository.
  - Platform-level: DPKG/RPM (Linux), Chocolatey (Windows), Package Manager (Android), Homebrew/MacPorts (macOS).
  - Language-level: npm (Node.js/JS), Gradle/Maven (Java), RubyGems (Ruby), Pip/Conda (Python).

**Introduction to Software Stacks**
- A **software stack**: a hierarchical combination of technologies (software + languages) that work together to run an app — higher layers serve the user, lower layers talk to the hardware. Typically split into **front-end** (languages, frameworks, UI tools) and **back-end** (languages, frameworks, web/app servers, OS, messaging, databases).
- "**Technology stack**" is the broader term — it includes hardware/infrastructure (VMs, containers, storage, load balancers) on top of the software stack.
- Simplest version = 3 layers: presentation, business logic, data. Complex apps add layers for virtualization, orchestration, runtime environments, DB connectivity, networking, security. No formal required structure — only use the layers relevant to your solution.
- Named stacks:
  - **Python/Django** — open source, good for large-scale, fast-changing web apps.
  - **Ruby on Rails** — strong with JSON/XML for data, HTML/CSS/JS on the front-end.
  - **ASP.NET** — Microsoft stack: ASP.NET MVC, IIS web server, SQL Server, Azure.
  - **LAMP** (Linux, Apache, MySQL, PHP) — an early, fully open-source, loosely-coupled stack; parts swap easily (MySQL → PostgreSQL = **LAPP**, PHP → Python, etc.).
  - **MEAN** (MongoDB, Express.js, Angular, Node.js) — platform-agnostic, free, open source.
  - **MERN** — MEAN with React instead of Angular (flexible, high-performing front-end).
  - **MEVN** — MEAN with Vue.js instead of Angular (lighter-weight, fewer built-in capabilities, but can outperform Angular).
- **Pros/cons** — MEAN vs. MEVN vs. LAMP:
  - **MEAN**: single language (JavaScript) end-to-end, open source (cheap, well-documented, lots of reusable Node modules for fast development). Weaker for large-scale apps — business logic tends to get stuck server-side in Express (limiting reuse of things like batching), and MongoDB, while great for unstructured data, lacks relational-DB-level functionality.
  - **MEVN**: same trade-offs as MEAN, but Vue is newer with a smaller library ecosystem than Angular.
  - **LAMP**: open source with a mature ecosystem (easiest to find support/reusable solutions, being one of the oldest stacks) — but less flexible since Linux is baked in (vs. MEAN/MEVN's platform-agnostic design), MySQL is relational (no unstructured-data advantage), and the back-end (PHP/Perl/Python) and front-end (JS/HTML) use different languages — a harder context-switch than an all-JavaScript stack.

**Insiders' Viewpoint: Tools and Technologies**
- **Git/GitHub** came up as near-universal in practice — used daily for tracking code, collaboration, and bug/feature/task tracking across both open- and closed-source projects. Most valuable with a team (feature branches, pull requests), but recommended even solo, partly for GitHub's community aspect.
- Real-world learning path example: static sites → adding dynamic content via JavaScript → picking up a back-end language (Java, PHP, or staying in JS via Node.js) — sticking with JavaScript end-to-end (via Node) makes the front-end-to-back-end jump easier.
- Tooling recommendations: a front-end-specific IDE (e.g., Brackets) or a general one (VS Code is the common recommendation), plus linting/formatting extensions (ESLint, Prettier) to catch issues early. Back-end tooling is far less standardized — Node.js reuses the same front-end tools; otherwise, research the linter/formatter ecosystem for whatever language you're using.
- JavaScript is powerful but easy to misuse — recommended discipline: proper variable/function scoping and writing unit/integration tests.
- Frameworks/libraries practitioners called out: **React** (Facebook) and **Angular** (Google, built for single-page apps) as leading front-end frameworks; **jQuery** (2006, John Resig) as one of the oldest/most-used libraries, often paired with Angular/React; **Backbone.js** as a lightweight alternative. Back-end: **Node.js** (built on Chrome's V8 engine, async single-threaded, handles high concurrency well), **Flask** (Python), and **Spring** (Java, long-standing and still widely used).
- Practitioner opinions favored **React** over Angular for speed/efficiency and ease of learning (easing team adoption), avoiding cross-browser issues, and its use of **JSX** (lets you work with UI markup inside JS, with clearer error/warning messages); one engineer specifically praised React's component-driven architecture and its props/state model for managing app state.
- **Express.js** (paired with Node/V8) was praised for fast scaling, using one language (JS) across front- and back-end, built-in caching, and faster page loads.
- Everyday go-to packages mentioned: **Axios** (for web requests — proper headers, callbacks/promises) and various npm database-connector packages (relational or NoSQL).
- **ES6** features (arrow functions, the spread/rest `...` operator, etc.) were recommended for writing cleaner, more readable JavaScript once the fundamentals are down.

### Module 3: Basics of Programming

#### Section 1: Programming Languages and Organization

**Interpreted and Compiled Programming Languages / Insiders' Viewpoint: Types of Languages (compiled vs. interpreted)**
- Programming languages exist because computers only understand **machine code** (binary); languages give us a human-readable way to write instructions.
- Two broad categories: **interpreted** and **compiled** — which one fits depends on the project's purpose.
- **Interpreted** (aka **scripting**) languages: run through an **interpreter** (built into a browser, or a program on your computer) that translates the human-readable code to machine code as the program runs. Examples: **JavaScript** (runs via the browser's interpreter), **Python** (popular for being easy to learn/use), **Lua** (lightweight, general-purpose game scripting).
- **Compiled** languages: a **compiler** converts the source code to machine code ahead of time and packages it into one executable file, which then runs when you open the app/icon. Runs faster and repeatably since translation is already done. Used for larger, more complex programs (apps, operating systems). Examples: **C, C++, C#** (used across Windows/Mac OS/Linux) and **Java** (distinct from the interpreted **JavaScript** despite the similar name — Android OS is written in Java). Operating systems themselves (Windows, Mac OS, Linux, Android) are written in compiled languages.
- **Practitioner add-on**: choosing compiled vs. interpreted is mostly personal preference and rarely affects development or deployment much either way; it matters more at the margins — e.g., squeezing small performance gains, or when you want the stronger guarantee that compiled code will behave and deploy as expected ("the buck stops with the compiler," so errors get caught before runtime). Interpreted languages trade that guarantee for more flexibility and "interesting runtime possibilities" — which language fits best depends on your environment and your risk tolerance for buggy code reaching production.

**Query and Assembly Programming Languages**
- Languages also split by **high-level** (English-like syntax, faster to write/debug) vs. **low-level** (a set of symbols representing machine code directly).
- High-level examples: **query languages** (e.g., SQL), **structured programming languages** (e.g., PASCAL), **object-oriented languages** (e.g., Python).
- Low-level examples: **assembly languages** (e.g., ARM, MIPS, x86).
- A **query** is a request for information from a database; a **query language** uses predefined, understandable syntax so an application and a database can communicate a request. **SQL** (Structured Query Language) is by far the most prevalent, though others exist (AQL, CQL, Datalog, DMX).
- **SQL vs. NoSQL** ("Not Only SQL"): SQL databases are relational with structured, predefined schemas; NoSQL databases are non-relational with dynamic schemas, suited to unstructured data.
- Queries/statements are either **select** (request/retrieve data) or **action** (create, insert, update — manipulate data), together covering **CRUD** (create, read, update, delete); statements can also handle admin tasks like creating users or setting permissions.
- **Assembly languages** are low-level and tied closely to processor architecture — each CPU type generally has its own, hence many exist. Written one statement per line: an **instruction/mnemonic** plus **parameters/operands**, with an optional trailing comment. Translated by an **assembler** (not a compiler or interpreter), and — unlike high-level languages, where one statement can expand into many machine instructions — one assembly statement maps to exactly one machine code instruction. Example mnemonics: INPUT/INP, OUTPUT/OUT, LOAD/LDA, STORE/STA, ADD. Statements consist of **opcodes** (what to do) and **operands** (where to find the data).

**Understanding Code Organization Methods**
- Planning code visually before writing it improves quality, readability, and maintainability, and reduces bugs — the two main methods are **flowcharts** and **pseudocode**.
- **Flowchart**: a pictorial representation of an **algorithm** (a step-by-step sequence for solving a problem) using shapes connected by arrows to show order/flow. Used to design or document a process, and to analyze different ways of solving a problem. Standard shapes: Start/End (capsule), Process (rectangle), Decision (diamond), Data (parallelogram), Connectors (arrows) — e.g., a flowchart for adding two numbers: Start → input n1, n2 → process Sum = n1 + n2 → output Sum → End. Flowchart software (Visio, Lucidchart, Draw.io, DrawAnywhere) provides drag-and-drop shape editors plus team collaboration.
- **Pseudocode**: an informal, high-level description of an algorithm's logic, independent of any specific language's syntax — a bridge between a programmer's thinking and the actual code. Lets programmers focus on logic over syntax, is easy for non-programmers to read, translates quickly into any language, and is easy for different teams to review and revise — usually under a page.
- Flowcharts suit smaller concepts/problems and are a faster, easier starting point early on; pseudocode is more efficient for larger projects and doesn't lock you into a particular language.

**Insiders' Viewpoint: Types of Languages (object-oriented vs. procedural)**
- **Object-oriented programming (OOP)** lets you model anything as an object and impose hierarchy/patterns on those objects, which helps keep a design's structure and object-to-object interactions organized — but overdoing it leads to excessive, boilerplate-heavy structure; the real skill is balancing structure vs. flexibility for what you're building.
- **Procedural programming** feels more mathematical/like "pure engineering" to some, appealing to people who want to feel like they're working directly "in the machine" rather than modeling real-world entities.
- Which fits better is partly a matter of how your brain works — practitioners recommended trying both. OOP tends to map naturally onto real-world entities and data models (e.g., a classic first OOP project: a library system with book objects and a checkout process), which can make it an easier bridge from "building something physical" to "building with bits and bytes."

#### Section 2: Programming Logic and Concepts

**Branching and Looping Programming Logic**
- Two major types of programming logic: **branching** and **looping** — both built on **Boolean expressions** (only two possible values, true or false) and **variables** (values passed into a function/subroutine that can change based on conditions or input).
- **Branching**: the program follows a different set of instructions depending on whether conditions are met during execution; each possible pathway is a branch, and there's no limit to how many a program can have. Which branch runs depends on the values of the branching procedure's parameters — supplied by user input or by a previous procedure's output.
- Common branching statements/constructs: **if** (runs one code block if a condition is TRUE, a different one if FALSE), **if-then-else** (the "then" block runs only if the condition is true; the "else" extension guarantees one block — true or false — always runs), **switch** (routes control flow based on a variable/expression's value), **GoTo** (a one-way jump to another line of code — unlike a function call, control doesn't return afterward).
- **Looping**: repeats a sequence of instructions until a condition is met (e.g., a counter reaching a target value); if not yet met, execution returns to the start of the sequence and repeats; once met, execution falls through to the next instruction or exits the loop.
- Three basic loop types: **while** (condition checked *before* the body runs — body executes only if true), **for** (initializes once, then checks/compares a counter after each iteration, stopping when the check returns false), **do-while** (aka **exit-controlled loop** — condition checked *after* the body runs, so the body always executes at least once).
- Bottom line: branching decides *what* action to take; looping decides *how many times* to repeat an action.

**Introduction to Programming Concepts Part 1: Identifiers and Containers**
- **Identifier**: a custom name a developer assigns to reference a program component — a stored value, method, interface, class, etc.
- If an identifier stores data, it's either a **constant** (value never changes within the program — e.g., pi, a fixed cost or tax rate) or a **variable** (value can change during execution — e.g., a user-entered age, a game's high score).
- Constants are defined with a value once and reused by name — giving more readable code, and a single point of change if the value ever needs updating (versus hunting down every hardcoded instance).
- Variables can hold text, numbers, or other data types, and are the way to reference values that aren't known ahead of time (a username, filename, etc.) rather than hardcoding them, which isn't best practice. A variable can be given an initial value when declared, or left unassigned until the program sets it later.
- **Containers**: identifiers that reference multiple elements at once, avoiding the need for a separate variable per element (impractical past a handful of elements — e.g., storing 1,000 integers individually).
- **Array**: a fixed number of same-typed elements stored sequentially, indexed from 0. Declared as: data type → array name → max size in square brackets.
- **Vector** (aka **dynamic array**): resizes automatically as elements are added or removed, trading some memory overhead for that flexibility. Declared as: container type ("vector") → data type in angle brackets → name — no size needed up front since it's dynamic.

**Introduction to Programming Concepts Part 2: Functions and Objects**
- **Function**: a product of **modular programming** — splitting a program into separate components that each handle one task. A function is structured, stand-alone, reusable code that performs a single specific action; some languages call them subroutines, procedures, methods, or modules, but "function" is the common modern term.
- Functions take in data, process it, and return a result as output. Two kinds: **standard library functions** (built into the language, e.g., `print`) and custom functions a developer writes and can reuse repeatedly.
- How a function's code block is delimited varies by language — braces, begin/end statements, or indentation.
- Using a function has two steps: **define/create** it (a function keyword, a unique name, and the body statements), then **call/invoke** it (runs the function's actions with whatever parameters are supplied). Defining and calling are universal across languages; some (C, C++) also require a separate **declaration** step.
- **Object-oriented programming (OOP)**: focused on objects rather than functions — the focus of **procedural programming** instead. Procedural code uses methods that operate on separate data structures; OOP packages data and code together so an object operates on its own data.
- Objects have **properties/attributes** (data, stored in fields — called variables in some languages) and **methods/behaviors** (code, exposed as functions in some languages) — conceptually similar to real-world objects (a car, a washing machine), which likewise have possible states and behaviors, with more complex objects having more of both. Software objects can be anything: a Windows service, a user account, a database table, a system folder, etc.

### Module 4: Software Architecture, Design, and Patterns

#### Section 1: Software Architecture and Design

**Introduction to Software Architecture / Insiders' Viewpoint: Importance of Design and Software Architecture**
- Software design/documentation happens during the SDLC's design phase. **Software architecture** = the organization of the system — a blueprint the programmers use to build the system's interacting components, defining the system's fundamental structures/behavior, how components interact with each other and the operating environment, and the principles used to design it.
- Architecture captures the earliest design decisions — costly to change once implemented — and addresses **non-functional** aspects: performance, scalability, maintainability, interoperability, security, manageability.
- Why good architecture matters: balances differing stakeholder needs and gives the team a shared basis for communication; because these are the earliest decisions made, they shape/constrain later implementation decisions; well-designed architecture supports agility as requirements change, and extends the software's usable lifespan even as implementation details change underneath it.
- Architecture drives **tech stack** choices (the full list of technologies/languages/libraries/frameworks used) — since the chosen stack has to satisfy the architecture's non-functional requirements, architects need to know each option's trade-offs. It also drives choices about the **production environment** — the infrastructure (servers, load balancers, databases) that runs and delivers the app to end-users.
- Architecture artifacts (communicate the design to stakeholders, like blueprints for a house): the **SDD** (Software Design Document — technical specs covering a functional description plus assumptions, dependencies, constraints, requirements, objectives, and methodologies), the **architectural diagram** (components, interactions, constraints, and the architectural patterns in use), and **UML diagrams** (language-agnostic structure/behavior notation — covered in the next video).
- **Practitioner add-ons**: design/architecture answers "where are you going and what does the system need to handle" *before* you start coding — skip that and you risk writing code you later discover doesn't work, wasting the time spent on it. One practitioner framed it as **orchestration**: individual pieces can each be well-built but still add up to "a cacophonous mess" if the system as a whole wasn't designed for them to work together. Concrete planning questions raised: what data does a given service need and where does it come from; what else needs to consume that data and how does it get there; and — especially in **microservice** setups, where services live on separate servers — how data actually moves between them, since each network hop costs time and can cause slow pages or timeouts. Also flagged: **auth/identity** (how do you know who's calling and what they're allowed to do) and **scale** (something that works for one user or one region often breaks at global/million-user scale). Architecture doesn't need to be rigidly over-specified, but should answer three things: *what* you need, roughly *where* it will live, and *what it's responsible for* (scope) — planned with a multi-year horizon in mind, evolving incrementally (like repairing a building) rather than being re-architected from scratch every few years.

**Software Design and Modeling**
- **Software design**: documents a system's structural components and behavioral attributes before development happens. **Modeling** — visual/diagrammatic representation of the solution and its sub-components/interactions — is a core part of this, done via simple flowcharts or standardized methods like UML.
- **Structured design**: breaks a software problem into organized smaller solution elements — **modules** and **sub-modules** — arranged hierarchically. A well-structured design is **cohesive** (functionally related elements grouped together) and **loosely coupled** (modules weakly associated, so a change in one has minimal effect on others) — loose coupling underlies **service-oriented** and **microservices** architectural patterns, covered later in this module.
- **Behavioral models**: describe *what* a system does without explaining *how* — communicated via UML behavioral diagrams, including **state transition diagrams** and **interaction diagrams**.
- **UML (Unified Modeling Language)**: a standardized, programming-language-agnostic way to visually represent a complex system's architecture, design, and implementation. UML diagrams split into **structural** and **behavioral** classes. Advantages: lets teams plan features before coding (saves time/money), helps new team members or team-switchers ramp up quickly, eases communication between technical and non-technical audiences, and gives developers a visual map for navigating source code via module relationships.
- **State transition diagram** (behavioral): a collection of **states** and **events** — showing the states a system can be in and the events that trigger a transition between them (e.g., a clinic patient moving between "waiting," "testing," and "with the doctor").
- **Interaction diagram** (behavioral): models a system's dynamic behavior — how objects relate and communicate. A **sequence diagram** (one type of interaction diagram) shows communication between objects over time (e.g., a patient booking an appointment through an online portal).

**Object-Oriented Analysis and Design**
- **OOAD (Object-Oriented Analysis and Design)**: an approach for analyzing and designing a system that will be built using object-oriented programming languages (Java, C++, Python).
- **Objects** contain data and have behaviors (actions the object can perform). A **class** is the generic blueprint/template an object is created from; a specific object created from a class is called an **instance**, and creating one is called **instantiation** — e.g., a generic "patient" class vs. a specific instance for patient Naya Patel. A class defines generic attributes (properties and methods) that only get set to actual values once instantiated (e.g., a `LastName` property is just a placeholder until an object is created and assigned a real name); once instantiated, an object's methods can be called to make it perform actions (e.g., booking or canceling an appointment).
- OOAD suits systems that can be broken into interacting objects, letting multiple developers work on different objects/aspects of the application at the same time.
- **Class diagram** (structural UML diagram): shows a system's classes — each box represents one class with its attributes (properties/data and methods/actions) — and the relationships between classes. A **subclass inherits** its parent class's properties/methods and can add its own on top (e.g., nurse/doctor/technician as subclasses of "medical personnel," and specialist as a subclass of doctor — so doctors can do everything medical personnel can, and specialists everything doctors can).

#### Section 2: Software Architecture Patterns and Deployment Topologies

**Approaches to Application Architecture**
- **Component**: an individual unit of encapsulated functionality that's part of an app, working alongside other components. Six characteristics: **reusable** (works across different apps), **replaceable** (easily swapped for another component), **independent** (no dependencies on other components), **extensible** (behavior can be added without changing other components), **encapsulated** (bundles its own data/methods, hiding internal state/implementation), and **non-context-specific** (works across different environments — data that sets its internal state gets passed in, rather than baked in or reached for internally).
- Examples: an API packaged as a reusable component (e.g., an open-source API connecting a system to a database), a **data access object** (a database's interface component, letting the app switch databases without the app itself knowing), and a **controller** (decides which other components to call for a given event, controlling the flow of data between them).
- **Component-based architecture**: decomposes a design into these logical, loosely-coupled, independent components working together — a higher level of abstraction than object-oriented design.
- **Service**: like a component (a unit of functionality) but deployed independently and reused by multiple systems, focused on solving a business need. Key difference from a plain component: a service has exactly one always-running instance that multiple clients talk to. Layering: **services are made of components, components are made of objects** — a service is a type of component meant to be deployed independently of the overall system. Examples: checking a customer's credit, calculating a loan payment, processing a mortgage application.
- **SOA (Service-Oriented Architecture)**: services are loosely coupled and interface with each other over a network via a communication protocol — supports building distributed systems that deliver services to other applications.
- **Distributed system**: multiple services on different machines, coordinating by passing messages over a protocol like **HTTP** — appears to end-users as a single coherent system despite spanning multiple machines. Properties: shares hardware/software/data resources; **fault-tolerant** (a failing node/service doesn't stop the system, and the system can change during execution without interrupting service); runs activities concurrently (lower latency, higher throughput); scales as users grow; and machines can differ in hardware, OS, and language.
- **Node**: any network device that can recognize, process, and transmit data to other nodes. A distributed system = multiple interconnected nodes running one or more SOA services.
- Distributed systems generally use one or more of: **client-server, three-tier, peer-to-peer, or microservices** architecture — detailed next.

**Architectural Patterns in Software**
- **Architectural pattern**: a repeatable solution to a common software architecture problem. Patterns can share overlapping characteristics and be combined — though not every combination is compatible.
- **2-tier / client-server**: the server hosts, delivers, and manages most resources/services; the client holds the interface and requests data/services from the server; typically several clients connect to one server over a network. Example: a text-messaging app (client sends via a server to another client), or a database client connecting to a database server.
- **3-tier** (aka **n-tier** with more than 3 layers) — the most common architecture: horizontal tiers functioning as one unit, where a tier only talks to the tiers directly above/below it, related components share a tier, and changes in one tier don't affect the others. The three tiers: **presentation** (UI), **application/middle** (business logic), **data** (storage/management). Example: most web apps — a web server (UI) + application server (processes input) + database server (data).
- **Peer-to-peer (P2P)**: a decentralized network where nodes act as both client and server, sharing the workload; peers make some of their own resources (processing, storage, bandwidth) directly available to others without central coordination — contrast with client-server, where only servers supply resources. Useful for file sharing, messaging, collaboration, high-performance computing. Example: cryptocurrencies (Bitcoin, Ethereum) — every node is both client and server.
- **Event-driven**: built around **events** (anything causing a state change — e.g., a user's mouse click, or another part of a program). **Producers** listen for/react to triggers and publish events to an **event router**, which decides which **consumer** to push the event to (via an **event notification**); components are loosely coupled, which suits modern distributed systems. Example: ride-sharing apps (Lyft/Uber) — a ride request is an event routed to a consumer.
- **Microservices**: breaks an app's functionality into modular, independent **services**. **APIs** let applications share/modify each other's data and can be used to build a microservices architecture; an **API Gateway** routes client requests to the right service, while **orchestration** handles communication between services. Example: social media platforms — one account, multiple independent services (friend requests, ad targeting, content display).
- Patterns aren't mutually exclusive — e.g., 3-tier can also be microservice-based, or P2P can also be event-driven — but some combinations are impossible (P2P can't also be 2-tier, since 2-tier requires a strictly separate client and server, while every P2P node is always both).

**Application Deployment Environments**
- **Application environment**: the combined hardware + software needed to run an app — the app's code/binaries, its software stack (modules, libraries, third-party apps, middleware, OS), networking/infrastructure, and physical/virtual hardware (compute, memory, storage).
- **Pre-production environments** (the prep stages before release): **development** (where the app is actively coded — often just the developer's own workstation), **QA/testing** (where the QA team tests components), and **staging** (as close to production as possible, but not for general users).
- **Production**: the full solution stack (hardware + software + infrastructure) that runs the app for all users — must account for real-world **load** (potentially millions of concurrent users) plus non-functional requirements (security, reliability, scalability), making it more complex than the pre-production environments.
- Deployment options: **on-premises** (infrastructure lives in-house, often behind a **firewall** — more control/security, but the org owns all the maintenance, and it's typically pricier than cloud) vs. **cloud**, which comes in three models: **public** (shared infrastructure over the open internet, owned by a provider like AWS/Azure/Google Cloud/IBM Cloud — the most common, for its cost and scalability), **private** (infrastructure dedicated to one organization — can be on-prem or provider-managed, e.g., AWS also offers private cloud — more secure and customizable), and **hybrid** (a mix of public + private working together, aiming to balance cost, security, scalability, and flexibility).

**Production Deployment Components**
- A production **n-tier** deployment, top to bottom: **presentation tier** (front-end client apps) → everything below sits behind a **firewall** → **web tier** (a web load balancer distributing traffic across web servers) → **application server tier** (an app load balancer/proxy server routing to application servers) → **data tier** (database server, often with a high-availability replica for reliability). Not every deployment needs every component or tier.
- **Firewall**: a security device that monitors traffic between networks, permitting or blocking data per a set of security rules — a barrier that blocks viruses, malware, and hackers from reaching the internal network.
- **Load balancer**: sits between clients and a **server farm**, distributing traffic efficiently across multiple servers to prevent overload, maximize availability/responsiveness, and keep any one server from being overworked — while still returning correct data quickly and reliably.
- **Web server**: delivers content (pages, files, images, video) to a client, primarily responding to **HTTP** requests from a browser.
- **Application server**: runs the app's business logic server-side rather than the client running it locally — its job is enabling interaction between the end-user and that server-side code, which governs things like how data is created/stored/changed, transaction results, and what gets read from or written to a database.
- **Proxy server**: sits between two tiers, handling requests between them — can also double as a load balancer, optimizer, cache, firewall, source-obscurer, encryptor, or malware scanner, generally improving a network's efficiency, privacy, and security.
- **Database / database server**: a database is a collection of related, accessible data, managed by a **DBMS** (Database Management System), which connects the database to users/programs; the database server controls the flow and storage of that data, and the DBMS is what lets an application retrieve or manipulate it.

**Insiders' Viewpoint: Deployment Architecture**
- *(Practitioner commentary spanning architecture patterns, deployment environments, and release practices — not tied to one specific lesson video in this section.)*
- Deployment design should start from concrete questions: expected **scale** (user count, data volume/growth, how real-time data access needs to be), **regionality** (global vs. local), **logging** needs (for both internal and external analysis), **privacy** (e.g., data anonymization requirements), and mapping out the actual data flows.
- Infrastructure choice (serverless vs. a hosted back end vs. self-hosting) is a real architectural decision — though early in a career it's often already decided by the team/company you join.
- **SLOs** (Service Level Objectives): define upfront what "healthy" or "well-running" means for your system, monitor those metrics continuously, and have a mitigation plan ready for when they slip.
- **Microservices** and keeping code modular (avoiding one giant, bloated codebase) were called out as increasingly important for letting teams move and deploy quickly.
- **Testing** — specifically **TDD** (test-driven development) — was singled out as the single most important habit to build as a developer, even if it's not always followed 100% of the time in practice.
- **Canary releases** ("canary in a coal mine"): rolling new code out to a small subset first to check whether it breaks anything before a full release — tied to the broader questions of how fast you need to ship, and how fast you need to be able to roll back if something goes wrong.

### Module 5: Job Opportunities and Skillsets in Software Engineering

#### Section 1: About Software Engineers

**What Does a Software Engineer Do?**
- Software engineers apply engineering, math, and computing skills to design and build software that solves real-world problems — a good fit for analytical, problem-solving-minded people.
- They build many kinds of software (desktop, web, mobile, games, operating systems, network controllers) using programming languages, development environments, frameworks/libraries, databases, and servers.
- Two categories: **back-end engineers** (aka **system developers**) — build the underlying computer systems/networks that front-end applications rely on; and **front-end engineers** (aka **application developers**) — more client-focused, building what users directly interact with (Android/iOS/Windows apps, platform-agnostic websites).
- Software types/settings: **off-the-shelf**, **bespoke** (built to a specific client's requirements), or **internal** (for users within your own organization). Within a team, work often falls into **data integration layers** (pulling data from various sources into the solution), **business logic** (applying real-world rules to that data), or **user interfaces**.
- Typical day-to-day tasks: taking user specs and designing new systems, writing and testing code, evaluating new software, optimizing for efficiency, maintaining/updating existing systems, documenting code for other developers, and presenting new systems to users/customers; **DevOps** practitioners also integrate and deploy their code to the underlying infrastructure. Beyond building your own systems, you'll also test, improve, and maintain code built by colleagues.
- Responsibility scope grows with seniority: **junior** roles are narrow (writing, testing, deploying, documenting code); **senior** roles carry primary responsibility across multiple areas of a solution, including the planning and design phases.

**A Day in the Life of a Software Engineer**
- *(A first-person narrative, not a formal lesson — illustrates what a normal day can look like rather than teaching new concepts.)*
- A day typically threads together: a **standup** (yesterday's progress/today's plan), **focus time** on a specific task, code review via **merge requests** (giving and receiving feedback, including from a mentor), handling an incoming **bug report** (fix → write/run a test case → resolve), and picking up new work from a cross-team request.
- Recurring themes worth remembering: regular feedback from more experienced teammates is a normal, expected part of the workflow (not just for juniors); being asked to work in an unfamiliar tool/framework (here, React) is treated as a routine opportunity rather than a blocker; and self-directed learning (docs, videos, reviewing a colleague's existing code for ideas) is just part of the job, not extracurricular.

**Skills Required for Software Engineering**
- **Hard skills**: practical, technical skills needed to design, build, maintain, and repair software — learned (school/college/university, online courses, certificates, or years of experience) and quantifiable/certifiable. Common examples: programming languages, version control, cloud computing, testing and debugging, monitoring, troubleshooting, agile development, database architecture.
- **Soft skills**: personal characteristics and interpersonal skills — less tangible, harder to define/quantify/certify than hard skills, but more easily transferable across roles and industries since they're not tied to a specific tech stack. Every real job requires a combination of both.
- Hard-skill detail: **software analysis and design** (understanding user needs, designing solutions to meet them), **programming/coding** (currently in-demand languages: Java, Python, C#, Ruby — employers will often accept experience in any language if you're willing to cross-train into theirs), understanding **frameworks** and **OOP principles**, **testing** (does the code meet the functional spec and is it usable), **debugging** (figuring out why code isn't working as expected), **deployment** (shell scripting, containers, CI/CD tooling), **monitoring** (reviewing a solution's live performance), and **troubleshooting** (resolving issues as they arise).
- Soft-skill detail: **teamwork** (project- or role-based teams, agile **squads**, pair programming — leverages individual strengths and builds new knowledge), **communication** (with peers, managers, clients, and users — each requiring a different angle), **time management** (deadlines matter more as teams span time zones, where a small local delay can cost someone elsewhere a full day), **problem-solving** (needed across design, development, testing/debugging, and ongoing maintenance), **adaptability** (to changing requirements — client change requests, shifting manager priorities, user feedback), and **openness to feedback** (peer code review, mentor guidance in junior roles, stakeholder feedback on releases — all aimed at making both the solution and the engineer better).

**Insiders' Viewpoint: Advice to Future Software Engineers**
- Practice constantly and keep learning new skills — use free resources to actually build projects, not just study passively. It doesn't matter if the project's been done before; what matters is building it yourself with the tools you've learned.
- Find a **business domain** you're genuinely interested in — not necessarily the easiest path, but one with problems you actually want to grapple with. This focuses both what you study and what jobs you target; interests vary person to person (e.g., someone drawn to machine learning will look for ways to apply it to whatever business problem they're working on).
- Don't be afraid to fail — the field has a lot of ongoing opportunity and movement, so a job or company not working out isn't really a failure; there are plenty of other roles and companies to move to.
- Practical job-search approach: pick a target role, list the skills it requires, and find free or low-cost resources to learn them.
- Be wary of buzzword-driven hiring and marketing ("hot new tech") — ask clarifying questions and make sure you actually understand what you're getting into before committing.
- Don't neglect the job-hunt process itself — treat it as its own skill to work on in parallel with the later half of your learning journey, rather than only starting it once you feel "done" learning, which risks a frustrating gap afterward.

**Insiders' Viewpoint: Women in Software Engineering**
- The industry has seen positive momentum toward diversification and making software engineering more welcoming to women, though many practitioners still describe early experiences of being the only, or one of very few, women on a team.
- Advice for that feeling of isolation: remind yourself you belong — everyone started out not knowing what was going on, and capability builds over time.
- Watch for role/title creep: if your job is software development, make sure diversity-related extra work (organizing initiatives, diverse hiring events, training) doesn't crowd out the actual coding you'll be reviewed and evaluated on — get compensated and titled for whatever work you're actually doing, and make sure that kind of extra labor doesn't fall disproportionately on one person.
- When choosing a team, it's fair to directly ask a hiring manager about their diversity plans and programs, and to look for a team that actively supports and advocates for women.
- You're not solely responsible for fixing an unwelcoming environment — it's fair to speak up, and reasonable colleagues should be able to take that feedback; you don't have to be the one who "does all the changing."
- If a team or company genuinely isn't a healthy, supportive environment, it's okay to leave — that reflects on the company, not on you. Companies genuinely serious about diversity and inclusion will have real programs in place to support and advance women, including into senior leadership.
- General job-search advice applies here too: figure out the target role, and take advantage of the free/low-cost programs specifically aimed at women entering or advancing in computing, given how underrepresented women remain in the industry.

#### Section 2: Careers in Software Engineering

**Job Outlook for Software Engineers**
- High demand drivers: virtually every industry needs software to compete and grow; most organizations need internal and/or customer-facing apps and websites; the **Internet of Things** keeps expanding the need for software that interacts with physical products; competitive pressure between vendors (rival products chasing each other's feature releases) keeps generating demand for more engineers.
- US outlook (per the Bureau of Labor Statistics): a **22%** job growth rate (2020–2030) for software developers/analysts/testers — well above average — roughly 200,000 openings a year in the US alone, spanning many industries (mobile, health, insurance, etc.), with a notably large predicted increase in security software roles as cyber threats grow.
- Education: most engineers hold degrees in software engineering or CS, but employers (IBM, Google, Tesla, and others) increasingly hire skilled non-graduates too — widening access to the field beyond the cost of a degree.
- Compensation (US): roughly $90K (junior) up to $120K+ (experienced), averaging around $110K/year — more than 2.5x the US average base salary — plus common benefits (bonuses, medical insurance, gym membership, profit share, retirement plans).
- What to expect day-to-day: dress codes are usually casual unless you're client-facing; flexible hours often built around a core midday window; occasional required meetings/calls; hours tend to climb near release dates (not always with matching pay); remote-work flexibility varies by employer, though there's no technical barrier to it — some teams are distributed globally across time zones.
- Employers span the spectrum: **FAANG**-scale tech companies (Facebook, Amazon, Apple, Netflix, Google) down to mid-size software companies, small houses/startups, and virtually any large non-tech company (banks, retailers, pharma) that needs internal or external systems. Most employers encourage continual learning (technical and soft skills) and invest in keeping staff skills current.
- Employment options beyond a traditional full-time role: apprenticeships/internships, part-time work, independent contracting/consulting (time- or project-based), freelancing, and volunteering on open-source projects (builds experience, skills, and visibility while supporting causes you care about).

**Career Paths in Software Engineering / Insiders' Viewpoint: Career Paths**
- As experience and skills grow, a software engineering career typically branches **technical** (staying hands-on with code) or **managerial** (leading a team) — titles vary by organization, but the roles are broadly consistent across the industry.
- Common progression: **Junior/Associate Software Engineer** (small, well-defined chunks of code, mentored) → **Software Engineer** (more independent, breaks larger tasks into sub-tasks, learns new languages/the SDLC, may start mentoring juniors) → **Senior Software Engineer** (whole-project/whole-codebase involvement, mentors others, runs code reviews, solves a wide range of problems efficiently).
- Technical branch continues: **Staff Software Engineer** (develops/maintains/extends software, ensures it meets user expectations and uses resources efficiently) → **Principal Engineer/Technical Architect** (owns architecture and design as well as development, sets team processes/procedures, provides technical direction).
- Managerial branch: **Technical Lead** (manages the dev/engineering team, may own the whole SDLC, reports to stakeholders) → **Engineering Manager** (ensures the team is supported and able to progress in their careers) → **Director of Engineering** (a strategic + technical role: sets project priorities, identifies hiring needs, defines long-term goals, defines requirements and oversees new projects) → **CTO** (oversees all company R&D, monitors systems/infrastructure against needs and budget, decides which emerging technologies to adopt for competitive advantage — still a continual-learning role even at the top).
- Not everyone follows this ladder — the underlying skills transfer well into adjacent roles: prefer talking to clients over writing code → technical sales/customer support; prefer data over general coding → data engineer/data scientist, and further into the data side → database administrator/developer; enjoy finding and fixing bugs → software tester. Starting in software engineering is a flexible stepping stone into many technical or leadership paths, not a one-way track.
- **Practitioner add-ons**: real entry paths into the field are often non-linear — backgrounds mentioned included social work (discovered coding via social media, then an intensive bootcamp), applied math (drawn in through a MATLAB-based research program), and fine arts/teaching (via a community-college class plus self-teaching, then grad school and an internship that converted to full-time). Common thread: a CS/technical degree isn't a prerequisite — plenty of strong engineers come from non-technical backgrounds and picked up coding on the side. For staying current post-hire: following tech commentators/newsletters (e.g., a "TLDR"-style digest), using employer-provided learning benefits (e.g., Udemy for Business), learning driven by an actual project's needs rather than abstract study, checking community discussion (e.g., Reddit threads) to gauge what's currently popular, reading documentation, leaning on well-informed coworkers, and — called out specifically — treating **debugging** as nearly as important a skill as writing the code in the first place.

**Software Engineering Job Titles**
- "Software engineer" / "software developer" are broad umbrella titles covering many sub-roles; company-specific titles vary, but generally map onto a set of generic ones: **front-end engineer, back-end engineer, full-stack engineer, DevOps engineer, software QA engineer, software integration engineer, software security engineer, mobile app developer, games developer**.
- **Front-end engineer** (aka UI/web developer): builds the user interface — visual design, UI layout, overall aesthetics; needs to understand UX principles and how code renders differently across OSes, devices, and browsers. Key skills: web development languages, UX/UI frameworks.
- **Back-end engineer**: owns the business logic — implementing core functionality (data/database access, logging, caching) via APIs, and ensuring scalability/performance. Key skills: programming languages, application frameworks, web/app servers, load balancers, databases, deployment/containerization tools.
- **Full-stack engineer**: works across the entire solution, combining front-end and back-end skill sets. Key skills: web dev languages, programming languages, UX/UI + back-end frameworks, web/app servers, databases, APIs/web services, deployment/containerization tools.
- **DevOps engineer**: blends development and IT operations to deliver software in an agile way, bridging traditionally separate dev/ops teams — needs familiarity with both front-end and back-end technologies. Key skills/tools: source code management, programming languages/frameworks, scripting, deployment/containerization/monitoring tools.
- **Software QA engineer** (aka software test engineer): tests, reviews, assesses, and writes software to validate quality — builds automated tests/tools/procedures, logs bugs via tracking software, and reports them to the dev team. Key skills: programming languages, shell scripting, bug-tracking/issue-management tools, test-automation tools, relevant stack knowledge.
- **Software integration engineer**: writes code that integrates software into hardware products (smart devices, IoT) — e.g., programming consumer devices, home security systems, electronics. Key skills: programming languages, proprietary technologies/frameworks/toolkits.
- **Software security engineer** (aka white-hat/ethical hacker): finds security flaws and vulnerabilities before release by building systems/methods to test and exploit weaknesses so they can be fixed. Key skills: programming languages, reverse engineering, shell scripting, vulnerability/pen-testing tools, network security/encryption tools.
- **Mobile app developer**: designs and builds software for phones/tablets — front-end web skills plus platform-specific back-end code. Key skills: mobile OSes, web dev languages, programming languages, web services/technologies.
- **Games developer**: writes gaming software across platforms (PC, mobile, browser, consoles), working alongside graphic artists, sound technicians, and game designers.

**Code of Ethics**
- The **Software Engineering Code of Ethics** was developed by a joint task force of the **IEEE Computer Society (IEEE-CS)** and the **ACM (Association for Computing Machinery)**, in recognition of computing's central role in commerce, government, and society — meant to keep software engineering a respected, accountable profession.
- Applies across the full lifecycle — specification, analysis, design, development, testing, maintenance — and to anyone connected to the profession (engineers, mentors, instructors, managers, students, policymakers), always in service of the public interest.
- Eight principles, in order: **Public** (act primarily for the public good — safety, fairness, accessibility, integrity), **Client and employer** (act in their best interests, be honest about unethical conduct like plagiarism or illegal activity, seek consent where needed, honor confidentiality), **Product** (aim for quality while respecting cost and timeline constraints), **Judgment** (maintain integrity, independence, objectivity, and honesty — avoid bribery, double billing, or conflicts of interest), **Management** (managers/leaders follow these same principles as they apply to their role — minimize risk, use security procedures, set realistic expectations, ensure fair compensation, secure IP rights appropriately), **Profession** (protect the field's reputation — act with integrity, don't self-promote at others' expense, disclose intent to follow the code, flag violations), **Colleagues** (treat peers with respect and fairness, encourage compliance with the code, don't take credit for others' work), and **Self** (commit to lifelong learning and professional development, strive for quality and professionalism).
- The code supplements, rather than replaces, an engineer's own judgment and common sense — knowing when and how to apply it is still up to individual discretion.
